# RS-04 — Descarga e instalación segura de APK

Implementación para auditoría independiente, siempre en PR Draft. Depende de
[PR #4, RS-03](https://github.com/robdor80/RobStore/pull/4), abierta y sin fusionar.
La rama `codex/rs-04-descarga-instalacion-segura` parte exactamente de
`8a0f3046c5695ae9e3e949dd9f782fcc3da835be`, nunca de main.
Base provisional: `codex/rs-03-ux-visual-robstyle`. No cambiarla ni fusionar hasta
fusionar RS-03, recibir autorización para ajustar la base y completar auditorías
y pruebas físicas. No incorpora RS-05 ni modifica el contrato robstore.json v1.

## 1. Arquitectura final

Un módulo Android, Kotlin/Compose/Material 3/RobStyle, SDK 36/36/26, JDK 17,
OkHttp, Navigation Compose y dependencias existentes. Sin bibliotecas nuevas.

- `catalog/CatalogValidation`: política común para descubrimiento, caché y selección.
  Cierra la brecha de campos sensibles de `validCachedApp`: ID, URL, digest y paquete.
- `CatalogDiscovery.revalidate`: reconsulta repositorio público, propietario/topic,
  última Release estable, manifiesto de su etiqueta y asset. Exige coincidencia
  completa con la selección del snapshot antes de descargar; si cambia, bloquea.
- `download/BinaryClient`: cliente exclusivo de binarios streaming y redirecciones.
- `DownloadCancellation`: cancela la Call real, también durante lecturas bloqueadas;
  comparte un plazo global monotónico de 15 minutos con la revalidación REST.
- `DownloadFiles`: rutas privadas generadas, espacio, temporales y limpieza.
- `ApkVerifier`: SHA-256, tamaño, parser oficial Android y paquete esperado.
  Solo él crea la capacidad interna `PreparedApk`; el estado UI no contiene rutas.
- `DownloadCoordinator`: un trabajo por ViewModel, StateFlow, cancelación real,
  confirmaciones y revalidación antes de entregar una capacidad al instalador.
- `install/AndroidInstaller` y `SystemActivity`: permiso, URI, intent interactivo y
  errores de actividades. `MainActivity` posee los launchers de resultados.
- `ui/DownloadActions`: presentación RobStyle y callbacks; sin red, archivos o permisos.

Se separan download/ e install/ porque transportar/verificar un archivo y solicitar
una acción interactiva de Android tienen límites y pruebas diferentes. Se conserva
el ViewModel existente para retener el trabajo al rotar y navegar. No hay Hilt,
Room, WorkManager, DownloadManager, servicios, notificaciones o descargas al arrancar.

## 2. Flujo de descarga

1. Pulsar **Descargar APK** en una ficha. Solo se pasa el ID del repositorio.
2. Resolverlo exclusivamente desde un CatalogSnapshot válido y revalidar sus campos.
3. Reconsultar GitHub, con presupuesto/paginación/cuotas RS-02, y contrastar la selección.
4. Comprobar espacio libre y abrir la URL inicial oficial validada.
5. Seguir como máximo tres redirecciones autorizadas; recibir bloques de 64 KiB.
6. Escribir un UUID `.part`; comprobar límites durante cada bloque y tamaño final.
7. Calcular SHA-256 del archivo real y analizarlo con Android, fuera del hilo UI.
8. Publicar atómicamente el archivo en `verified/` solo si supera todos los controles.
9. Mostrar SHA coincidente o advertencia sin referencia oficial. Nunca abrir el
   instalador al terminar una descarga.

Solo un trabajo activo: pulsaciones repetidas u otra aplicación se rechazan hasta
terminar/cancelar. Otra ficha muestra la operación actual y permite cancelarla.
Mientras Android mantiene abierto el instalador no se reemplaza su APK. Después,
una nueva descarga elimina el APK preparado anterior. El estado no persiste entre
procesos; no existe reanudación automática.

## 3. Política de origen

Propietario exacto `robdor80`, repositorio canónico y seguro, ID de repositorio y
Release positivos, etiqueta segura, asset ID positivo, nombre `.apk` permitido,
1 byte–512 MiB, SHA opcional de 64 hexadecimales y packageName válido.
URL inicial HTTPS, puerto 443, host exacto github.com, sin credenciales, consulta
ni fragmento; segmentos exactos propietario/repositorio/releases/download/tag/asset.
Se rechazan normalizaciones de rutas, credenciales, dominios parecidos y datos
inconsistentes de caché. La política compartida evita divergencias entre red y disco.
La revalidación remota detecta también alteraciones sintácticamente válidas de IDs,
paquete, digest o tamaño. Si la última Release cambia, hay que refrescar el catálogo.
GitHub no ofrece una transacción entre sus recursos: persiste un intervalo entre
consultar metadatos y recibir el binario; SHA, tamaño y paquete reducen ese riesgo.

## 4. Redirecciones permitidas y HTTP

Allowlist **exacta**, sin reglas de sufijo:

| Momento | Host permitido |
| --- | --- |
| Primera solicitud, URL de asset validada | github.com |
| Destino de redirección oficial | release-assets.githubusercontent.com |
| Destino de redirección oficial | objects.githubusercontent.com |

Se admiten consultas firmadas de CDN únicamente después de una redirección válida.
Otros dominios, subdominios, HTTP, puertos distintos, credenciales, fragmentos,
backslash y controles se bloquean. Un host oficial adicional necesita revisión
y pruebas antes de ampliar esta lista. No se registra ninguna URL firmada completa.

TLS normal del sistema, sin CA/trust managers propios, sin autenticación/cookies.
Headers públicos reconstruidos en cada salto. Redirecciones y reintentos automáticos
OkHttp deshabilitados. HTTP 200 directo y 301/302/303/307/308 controlados; bucles y
cuarto salto bloqueados. 403/404/429/5xx, 204/206, fallos de red y timeouts son errores,
sin instalar ni reintentar automáticamente. El bloqueo de cuota REST se comparte
con la caché RS-02; la descarga binaria solo admite reintento manual.

Conexión 15 s, lectura binaria 30 s, llamada binaria 5 min; las Calls REST conservan
30 s. El token limita cada Call al tiempo restante del plazo global de 15 min.
La recepción también comprueba un límite monotónico de 10 min. No hay bucles infinitos.
Content-Length, cuando está presente, debe ser único, válido y exacto; se rechaza
su combinación ambigua con Transfer-Encoding. Se prohíben cuerpos comprimidos.
Sin Content-Length se verifica igualmente el recuento exacto durante y al terminar.

## 5. Integridad y límites de verificación

MessageDigest SHA-256 procesa el archivo en bloques de 64 KiB; nunca se carga un
APK completo en memoria. Si existe referencia SHA-256 válida de GitHub, cualquier
diferencia elimina el archivo y bloquea instalar. Un digest malformado se rechaza
antes de la descarga. Siempre se comprueban tamaño final, cabecera ZIP/APK,
metadatos reconocidos por Android y packageName interno exacto del catálogo.

Sin digest oficial se calcula el hash local y se muestra una advertencia explícita;
no se afirma integridad frente a una referencia del editor. Es obligatorio pulsar
**Acepto continuar sin SHA oficial** antes de mostrar Instalar. Con SHA coincidente
se muestra ese hecho y una acción Continuar. Ambas rutas requieren luego Instalar.

Parsear el paquete **no verifica criptográficamente su firma**, y un SHA publicado
por GitHub no demuestra por sí solo autenticidad del editor. La comprobación final
de firma, compatibilidad y decisión de instalar corresponde al instalador Android.
Antes de cada solicitud de instalación se vuelve a leer/hash/parsear el archivo,
se compara también el hash local guardado y se comprueba que la selección siga
siendo la misma en el catálogo actual. Alteración, ausencia o caducidad bloquean.

## 6. Archivos y almacenamiento

Todo en `filesDir/apk-downloads/`, sin almacenamiento público ni nombres remotos
como rutas. La raíz se canonicaliza para admitir rutas privadas Android legítimas;
los archivos se generan por UUID y se rechazan rutas ajenas o enlaces del archivo.

- Temporales: UUID.part en la raíz, nunca accesibles por FileProvider.
- Preparados: UUID.apk en `verified/`, solo tras verificación y movimiento atómico.
- Espacio: tamaño completo + reserva de 8 MiB antes de empezar, reserva de 8 MiB
  comprobada antes de cada escritura durante la recepción.
- Cancelar llama Call.cancel y cancela el Job; use/finally cierran recursos y
  eliminan el parcial tras fallos HTTP, lectura, escritura o cancelación.
- Al iniciar una sesión se limpian huérfanos y preparados anteriores. Fallar la
  limpieza impide descargar. No hay tareas periódicas ni reanudación.
- Un único preparado retenido por sesión; caduca a las 24 h, o ante retroceso del
  reloj, y se elimina al detectar caducidad. Un proceso cerrado puede dejarlo en
  disco hasta el siguiente arranque: no hay servicio de limpieza en segundo plano.

Si Android pierde acceso al archivo tras matar/reabrir RobStore durante una
instalación, será necesario descargarlo de nuevo. No se persisten capacidades de
instalación ni se confía en archivos antiguos por el mero hecho de existir.

## 7. Instalación y permisos

REQUEST_INSTALL_PACKAGES; FileProvider no exportado, autoridad
`${applicationId}.apkfiles`, raíz XML exclusiva `apk-downloads/verified/`.
Intent ACTION_VIEW, MIME `application/vnd.android.package-archive`, URI content://
y ClipData con FLAG_GRANT_READ_URI_PERMISSION, sin escritura, file:// o permisos
amplios. Android decide si existe una actividad compatible; su ausencia/restricción
produce error recuperable. No hay instalación silenciosa ni sesiones complejas.

Tras **Instalar**, comprobar canRequestPackageInstalls(). Si falta autorización,
explicar el requisito y ofrecer ACTION_MANAGE_UNKNOWN_APP_SOURCES con
`package:<ID de la variante>`. Tanto el resultado del launcher como ON_RESUME
reconsultan el permiso. Regresar sin concederlo mantiene pendiente. Concederlo
solo habilita volver a pulsar Instalar: no abre automáticamente el instalador.

Distingue archivo preparado, permiso pendiente, instalador abierto/solicitud
entregada y resultado no confirmado. ACTION_VIEW no proporciona un resultado
fiable de instalación/cancelación; ni volver ni RESULT_OK/RESULT_CANCELED se
convierten en «instalación correcta». Solo se informan errores de lanzamiento
realmente detectables. No se consultan paquetes instalados ni versiones: fuera
RS-04. Los únicos metadatos Android leídos pertenecen al archivo APK seleccionado.

## 8. Estados RobStyle y accesibilidad

Disponible, comprobando origen, descargando con bytes/tamaño/porcentaje,
cancelando, verificando, SHA oficial coincidente, preparado sin SHA oficial,
preparado para instalar, permiso pendiente, preparando entrega, instalador abierto,
resultado no confirmado, error recuperable y bloqueo de seguridad/integridad.

Descargar/Cancelar/Reintentar/Instalar aparecen solo cuando corresponde. Los estados
no incluyen rutas ni URLs firmadas. Progreso Material 3 con semántica de rango;
solo el texto de fase usa LiveRegion Polite, sin anunciar cada bloque. Se conservan
paleta, tipografías, tarjetas y ancho máximo RS-03. Botones con tamaño táctil
Material y texto multilínea, ficha desplazable y pruebas al 200 %, 320/1200 dp.
Home, malla y Ajustes conservan estructura, navegación por repositoryId y pruebas.
El ViewModel sobrevive recreación; volver a una ficha no inicia otra descarga.

## 9. Errores conocidos y recuperación

Sin conexión, cuota agotada, espacio insuficiente o fallo de escritura: limpiar y
reintentar manualmente tras corregir la causa. Origen cambiado, digest, tamaño,
paquete o formato incorrectos: bloqueo sin instalar, archivo eliminado. Ante cambio
de metadatos, refrescar respetando RS-02. Un fabricante puede restringir el ajuste
por origen o carecer de instalador compatible: se muestra error, sin elusión.
No se puede confirmar el resultado real del instalador con este mecanismo.

## 10. Compatibilidad API 26–36

min 26 / target y compile 36. API 26–32 usa getPackageArchiveInfo(path, flags);
33+ usa PackageInfoFlags.of(0). versionCode se adapta a API 26/28+.
FileProvider y autorización por origen desde API 26. Pruebas JVM del parser y URI
en 26/33; Compose/identidades/launcher en 28. Compilar para 36 no certifica runtime
36 ni todas las personalizaciones OEM. No se afirma cobertura física de todo el rango.

## 13. Limitaciones Cloud y pruebas físicas pendientes

Cloud no traía JDK 17 ni SDK: se instalaron herramientas oficiales localmente,
ignoradas por Git; no se cambiaron versiones del proyecto ni validaciones.
Sin emulador ni dispositivo físico conectado. Renders Robolectric NATIVE no
certifican GPU, barras, tacto, TalkBack ni la UX específica del instalador OEM.

Pendiente en Realme GT Neo 2 y Galaxy Tab S9+, vertical/horizontal: descarga real
de una Release estable autorizada, red lenta/corte/cancelación, rotación durante
recepción, fuente 200 %, TalkBack, denegar/conceder/revocar permiso de origen,
volver sin permiso, abrir/cancelar instalación y errores de firma/compatibilidad.
No se han realizado ni inventado estas pruebas. Sin Releases reales utilizables,
la automatización usa fixtures; nunca se publican Releases de prueba para suplirlas.

## 14. Descargar RobStore DEV desde Actions en un móvil

1. Abrir la PR RS-04 y su check **Android / validate**, o [Actions del repositorio](https://github.com/robdor80/RobStore/actions).
2. Elegir la ejecución **pull_request** correcta y satisfactoria para el HEAD de
   la PR. Al final, Artifacts → `robstore-dev-<SHA completo>`; GitHub puede requerir
   iniciar sesión para descargar artefactos. Retención: 30 días.
3. Descargar el ZIP, extraerlo con Archivos/gestor local y localizar
   `RobStore-DEV-<12 caracteres del SHA>.apk`. Incluye SHA256SUMS,
   verificacion.md y firma-debug.txt (certificado público, nunca clave privada).
4. Abrir el APK extraído. Android puede pedir permiso de origen para el navegador
   o gestor de archivos que lo abre. Revisar que sea **RobStore DEV** y confirmar
   en el instalador Android. No se instala directamente desde dentro del ZIP.
5. La app DEV tiene ID `es.robertodorado.robstore.debug`, nombre RobStore DEV e
   icono oficial con D. Release conserva `es.robertodorado.robstore` y RobStore.

El workflow solo publica ese APK tras validación correcta en PR interna del
mismo repositorio; las ejecuciones push y PR externas no publican DEV. Conserva
permissions: contents: read. `verify_rs04_apks.py` comprueba el APK real: IDs,
nombres, SDK, permisos, zipalign, firma Debug válida y SHA-256. Release queda sin
firma privada. El checksum identifica los bytes del artefacto; no sustituye la
confianza en la cuenta/repo/workflow ni garantiza identidad del editor por sí solo.

Los runners efímeros pueden generar una clave Debug diferente en cada ejecución.
Una DEV previa puede rechazar actualizar por firma incompatible. Si ocurre, el
propietario puede desinstalar **solo RobStore DEV** y volver a instalar, perdiendo
sus datos locales. RobStore Release y otras apps son identidades independientes.
No se publica ni persiste una clave privada para evitar este inconveniente.
Este artefacto instala **RobStore DEV**; es distinto de los APK de aplicaciones
que RobStore descargará después desde sus Releases autorizadas.
