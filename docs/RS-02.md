# RS-02 — Catálogo automático RobStore

## Base y alcance

Se parte de `main` en `b221c3f94154e73676f3ad3a86755610e3be8045`.
GitHub confirmó que las PR [#1](https://github.com/robdor80/RobStore/pull/1)
y [#2](https://github.com/robdor80/RobStore/pull/2) están fusionadas. Se revisaron
README, RS-00, RS-01, pantallas, navegación, RobStyle, manifiesto, Gradle, tests y CI
antes de modificar archivos. No se detectaron diferencias respecto al estado esperado.

Un único módulo `app`; Kotlin 2.2.21, AGP 8.13.2, Gradle 8.13, JDK 17,
SDK 36/36/26, Compose y Material 3 conservados. Se añaden OkHttp 4.12.0,
kotlinx.serialization JSON 1.9.0 y Lifecycle 2.9.4. El plugin de serialización usa
la misma versión de Kotlin. Coroutines Test 1.10.2 solo se usa en tests.
No se modifican la CI, el arte launcher, la paleta, los IDs, las versiones ni las firmas.

Home descubre aplicaciones sin una lista fija y abre `app/{appId}` mediante el ID
numérico estable de GitHub, independiente del paquete Android. Detalle muestra
metadatos publicados, nunca una versión instalada. Instalar permanece deshabilitado.
Ajustes presenta origen, sincronización, política real y motivos de exclusión;
no incluye preferencias simuladas. Se mantienen tema oscuro, ancho máximo,
desplazamiento, texto adaptable y etiquetas accesibles.

## Arquitectura

Todo está en `app/src/main/java/es/robertodorado/robstore/catalog`:

- `HttpTransport` sustituible y `OkHttpTransport`: HTTPS, host API exacto,
  redirecciones y reintentos automáticos deshabilitados, límites durante la lectura,
  timeouts de conexión/lectura/llamada de 15/20/30 segundos. Sin autenticación.
- `GitHubClient`: REST, paginación, ETag/304, presupuesto de solicitudes y límites
  de GitHub. Un único transporte compartido serializa red de catálogo e iconos.
- `ManifestValidator`: contrato v1 y construcción de URLs desde segmentos validados.
- `CatalogDiscovery`: filtros, selección estable y validación exacta del adjunto;
  errores del contrato excluyen un repositorio con diagnóstico. Fallos de transporte
  o paginación abortan el resultado completo.
- `CatalogRepository`: arranque offline-first, refresco manual, exclusión mutua y
  conservación del snapshot anterior ante errores. Solo publica un nuevo catálogo
  después de persistirlo correctamente.
- `CatalogCache` / `FileCatalogCache`: JSON privado versionado, escritura temporal,
  `fsync` y sustitución atómica; archivo independiente para el intervalo y bloqueo.
- `CatalogViewModel`: enlaza el repositorio con `viewModelScope` y expone `StateFlow`;
  Compose lo recoge con `collectAsStateWithLifecycle`. IO y decodificación fuera del
  hilo principal. No hay DI externa, módulos adicionales ni trabajos programados.
- `CatalogIconLoader`: caché acotada de memoria/disco y decodificación PNG/WebP.
  Se utiliza este cargador pequeño en lugar de Coil para compartir el transporte,
  el control de cuota y los límites estrictos antes de decodificar.

Los modelos distinguen repositorio, Release, APK e icono. Incluyen nombre,
descripción, paquete, URL oficial, etiqueta, fecha, notas, ID/nombre/tamaño/URL del
APK, SHA-256 opcional, disponibilidad y referencia del icono.
`ApkVerification.NOT_PERFORMED` deja explícito que no se ha verificado firma ni
integridad local. El digest procede de GitHub y solo se conserva como metadato.

## REST y descubrimiento

Todos los GET son públicos, sin token, contra `https://api.github.com`:

| Recurso | Ruta |
| --- | --- |
| Repositorios | `/users/robdor80/repos?type=owner&per_page=100&page=N` |
| Releases | `/repos/robdor80/{repo}/releases?per_page=100&page=N` |
| Manifiesto | `/repos/robdor80/{repo}/contents/robstore.json?ref={tag}` |
| Adjuntos | `/repos/robdor80/{repo}/releases/{releaseId}/assets?per_page=100&page=N` |
| Icono | `/repos/robdor80/{repo}/contents/{ruta}?ref={tag}` |

Headers: `User-Agent: RobStore-Android`, `X-GitHub-Api-Version: 2022-11-28`,
`Accept: application/vnd.github+json`; contenidos usan
`application/vnd.github.raw+json`. La referencia se codifica como parámetro de
consulta; se admiten etiquetas con `/`, sin interpretar SemVer. No se utiliza
Search API, `/latest` ni la rama predeterminada para los recursos publicados.

Se aceptan exclusivamente propietario exacto `robdor80`, repositorio público,
no archivado y topic exacto `robstore-app`. Se valida también la URL canónica.
Un topic parecido, fork de otro propietario o repositorio privado no es candidato.

Cada listado continúa hasta una página de menos de 100 elementos. Máximo 10
páginas por listado, respuestas de hasta 2 MiB, anidamiento JSON máximo de 64 niveles,
IDs positivos únicos y máximo 50 peticiones por refresco
completo. Superar un límite o recibir páginas repetidas/inconsistentes es un fallo
incompleto: se conserva el catálogo anterior, sin publicar una lista truncada.
El listado específico de adjuntos evita depender de los assets embebidos en Releases.
Home utiliza `LazyColumn` para cargar tarjetas e iconos a medida que entran en pantalla.

## Contrato `robstore.json`, versión 1

Archivo UTF-8 en la **raíz del repositorio y en la etiqueta publicada**:

```json
{
  "schemaVersion": 1,
  "name": "Mi aplicación",
  "description": "Descripción de mi aplicación Android",
  "packageName": "es.robertodorado.miapp",
  "icon": "robstore/icon.png",
  "apkAssetName": "app-release.apk"
}
```

| Campo | Reglas v1 |
| --- | --- |
| `schemaVersion` | Número entero JSON `1`, obligatorio; no cadena ni otra versión |
| `name` | Cadena no vacía, máximo 120 caracteres |
| `description` | Cadena opcional, por defecto vacía, máximo 4000 caracteres |
| `packageName` | Obligatorio, máximo 255; al menos dos segmentos separados por punto, cada uno empieza por letra ASCII y continúa con letras, números o `_` |
| `icon` | Cadena opcional, por defecto `robstore/icon.png`; ruta segura PNG o WebP, máximo 240 caracteres |
| `apkAssetName` | Obligatorio; nombre exacto ASCII, 5–160 caracteres, empieza por letra/número/`_`, continúa con letras/números/`_`/`.`/`-`, termina en `.apk` minúsculo |

No se aceptan `null` explícitos para esos campos. Se ignoran campos desconocidos
para permitir extensiones informativas, sin aceptar versiones de esquema futuras.
Nombre, descripción y notas rechazan caracteres de control salvo saltos de línea,
retorno y tabulador. Los textos se representan como texto plano.

Las rutas constan de segmentos `[A-Za-z0-9_.-]+` separados por `/`. No se admiten
segmentos vacíos, `.` o `..`, inicio `/`, backslash, `%`, `:`, consultas, fragmentos,
URLs externas, rutas absolutas, traversal ni formatos distintos de `.png`/`.webp`.
`apkAssetName` es un nombre, nunca una ruta. El manifiesto no puede elegir el host.
Los nombres de repositorio se limitan a 1–100 caracteres ASCII seguros.

Máximo de manifiesto: **32 KiB**, validado también durante la lectura HTTP.
JSON corrupto o con anidamiento excesivo, UTF-8 inválido, esquema incompatible o campos incorrectos producen
una exclusión controlada. No se ejecuta contenido remoto ni se renderiza HTML,
Markdown activo o imágenes incluidas en notas de cambios.

## Releases y APK

1. Se examinan todas las páginas permitidas del listado de Releases.
2. Se descartan `draft=true`, `prerelease=true` y Releases sin `published_at`.
3. Se selecciona la mayor fecha oficial `published_at`; en empate, el mayor ID.
   Las etiquetas no se ordenan alfabéticamente ni como SemVer. Fechas malformadas
   en Releases estables excluyen el repositorio para evitar una elección insegura.
4. Se comprueban ID, etiqueta y fecha no futura de la elegida.
5. Se lee `robstore.json` con **`ref=tag_name` de esa Release**.
6. Se listan sus adjuntos y se exige exactamente una coincidencia con `apkAssetName`.

APK válido: ID positivo, estado `uploaded`, tamaño **1 byte–512 MiB**, extensión
`.apk` y MIME `application/vnd.android.package-archive` o
`application/octet-stream`. Su URL debe ser HTTPS, puerto 443 y host exacto
`github.com`, sin credenciales, consulta ni fragmento, con propietario, repositorio,
etiqueta y nombre exactos en `/robdor80/{repo}/releases/download/{tag}/{nombre}`.
El digest opcional debe ser `sha256:` seguido de 64 dígitos hexadecimales.

Si hay otros APK con nombres distintos se ignoran. Si el esperado falta, aparece
duplicado o tiene metadatos incorrectos, **se excluye la aplicación** y se registra
el motivo en Ajustes. No se anuncia una versión antigua como última. Un manifiesto
válido en `main` no subsana su ausencia en la etiqueta publicada.

Estas comprobaciones validan metadatos: no demuestran que el archivo sea un APK
real, que su paquete coincida ni que tenga firma válida. No se descarga el binario.

## Iconos

Convención: `robstore/icon.png`, preferiblemente cuadrado y hasta 512×512.
También se admite WebP. Se solicita desde el mismo repositorio y `ref` de la Release.
No se consulta ni extrae el APK. Si falta o es incorrecto aparece un icono RobStyle
con etiqueta accesible; el problema no excluye una aplicación distribuible.

- Lectura asíncrona en IO, máximo **512 KiB** por imagen.
- Solo MIME decodificado PNG/WebP; máximo 2048×2048 y 4 194 304 píxeles antes
  de decodificar. Muestreo para limitar el bitmap mostrado.
- Caché LRU en memoria de **8 MiB**, disco privado de **20 MiB**.
- Clave por repositorio, ID de Release, etiqueta y ruta; una nueva Release usa otra clave.
- Recursos ausentes/inválidos tienen caché negativa durante la sesión; los fallos
  transitorios de red pueden reintentarse al volver a abrir la pantalla.
- Los iconos consumen cuota REST si no están en caché y comparten el bloqueo
  por rate limit. El sistema puede eliminar la caché de imágenes; el catálogo
  persistente vive en `filesDir` y no depende de ella.

## Caché, actualización y errores

`filesDir/catalog/catalog-v1.json` guarda esquema 1, fecha de sincronización,
aplicaciones y diagnósticos. `refresh-v1.json` guarda el último intento y el límite
remoto. Límite del catálogo persistido: **4 MiB**. Una caché corrupta o de esquema
desconocido se ignora; archivos temporales interrumpidos no sustituyen al definitivo.
Copias y transferencia de datos continúan deshabilitadas en el manifiesto Android.

En un nuevo arranque se lee primero el snapshot privado en IO y se publica en
Compose antes de consultar la red. Si tiene menos de **2 horas**, no se refresca
automáticamente. Caducado o ausente provoca una comprobación si el intervalo y la
cuota lo permiten. Cambiar la hora hacia atrás no habilita un bucle de refresco.
No hay refrescos periódicos, WorkManager ni notificaciones.

«Refrescar catálogo» realiza una consulta real incluso con caché reciente, con un
mínimo de **5 minutos entre intentos completos**, incluidos los fallidos. Las
pulsaciones simultáneas se unen mediante exclusión mutua. Una pulsación durante
el intervalo informa de la fecha permitida sin simular éxito ni consultar GitHub.
El botón se deshabilita mientras se carga o actualiza. Reintentar respeta la misma
política, también tras reiniciar el proceso.

Un resultado completo con cero aplicaciones se persiste como catálogo vacío válido.
Errores de red, HTTP, páginas incompletas, cuota o disco conservan el último
snapshot y su fecha. Se muestra el fallo y, si procede, caché desactualizada.
Si nunca hubo un snapshot válido se muestra error con reintento; no se inventan apps.
Errores individuales del contrato sí producen un resultado completo con exclusiones.

Se conservan ETag y cuerpos en memoria (hasta **8 MiB**) para solicitudes
condicionales posteriores de la sesión. HTTP 304 reutiliza solo el cuerpo asociado
al ETag solicitado; un 304 sin cuerpo previo es error. La caché de ETags no persiste
entre procesos: el primer refresco de una sesión puede consumir toda su cuota normal.

## Límites de GitHub y consistencia

La cuota pública habitual es **60 solicitudes/hora por IP**, compartida con otros
clientes. No se presupone que el intervalo de 5 minutos garantice cuota disponible.
Con una sola app y una página por listado, un refresco usa 4 solicitudes; cada
candidato adicional añade normalmente 3, más páginas e iconos. Los repositorios
sin contrato también consumen las peticiones necesarias para excluirlos.

Se limita a una solicitud concurrente, sin reintentos automáticos ni bucles.
Se respetan `Retry-After` (segundos o fecha HTTP), `X-RateLimit-Reset` y
`X-RateLimit-Remaining`. HTTP 403/429 establece un bloqueo persistente: se utiliza
el mayor plazo indicado, con mínimo de 60 segundos; sin plazo útil, 15 minutos.
Un 403 de permisos se trata también conservadoramente. Una respuesta 200 que agota
la cuota puede usarse, pero impide nuevas peticiones hasta el reset.

ETag reduce transferencia; no se promete que todo 304 público sea gratuito.
El presupuesto de 50 peticiones y los topes de páginas priorizan conservar el
último catálogo completo. Catálogos grandes necesitarán revisar esta estrategia
antes de ampliar el alcance; no se ocultan por truncamiento silencioso.

REST no proporciona una transacción entre listados. Publicaciones o borrados durante
un refresco pueden causar error o no verse hasta el siguiente. IDs repetidos y
páginas incoherentes abortan. Se recomienda tratar etiquetas y Releases publicadas
como inmutables: el contrato usa la etiqueta, no un commit resuelto e inmutable.
Editar una etiqueta o recurso de una Release existente puede conservar un icono
anterior en caché; publicar una nueva Release evita esta ambigüedad.

## Preparar y publicar una aplicación nueva

Ejemplo para **un repositorio nuevo y público de `robdor80`**, con un proyecto
Android existente y su Wrapper. Estas instrucciones son para el propietario;
RS-02 no las ejecuta contra ningún repositorio ni crea Releases de prueba.

1. Usa un `applicationId` estable, por ejemplo `es.robertodorado.miapp`.
2. Añade el JSON completo del contrato anterior como `robstore.json` en la raíz.
3. Añade un PNG real como `robstore/icon.png`, hasta 512 KiB y dentro de los límites.
4. Compila un APK Release. Para distribución instalable configura tu firma fuera
   de Git; RobStore RS-02 solo validará los metadatos, no esa firma.
5. Versiona manifiesto e icono **antes de crear la etiqueta**, publica una Release
   estable con el adjunto exacto y añade el topic.

Ejemplo de comandos con Git y GitHub CLI ya autenticado **en el equipo del editor**.
La app RobStore nunca usa esa autenticación. Sustituye `MiAplicacion` por el nuevo
repositorio propio; se presupone `origin` y rama `main` del proyecto nuevo:

```sh
# Ejecutar en el nuevo proyecto Android, nunca como parte de los tests de RobStore.
mkdir -p robstore
cp /ruta/local/icono.png robstore/icon.png
cat > robstore.json <<'JSON'
{
  "schemaVersion": 1,
  "name": "Mi aplicación",
  "description": "Descripción de mi aplicación Android",
  "packageName": "es.robertodorado.miapp",
  "icon": "robstore/icon.png",
  "apkAssetName": "app-release.apk"
}
JSON
./gradlew test assembleRelease
# Copia el APK producido. Un proyecto con firma Release normalmente usa esta ruta:
mkdir -p dist
cp app/build/outputs/apk/release/app-release.apk dist/app-release.apk
# Si la compilación solo produce app-release-unsigned.apk, primero fírmalo fuera
# de Git para una distribución instalable; no publiques claves ni contraseñas.
git add robstore.json robstore/icon.png
git commit -m 'Añade metadatos de publicación RobStore v1'
git push origin main
git tag v1.0.0
git push origin v1.0.0
gh repo edit robdor80/MiAplicacion --add-topic robstore-app
gh release create v1.0.0 dist/app-release.apk \
  --repo robdor80/MiAplicacion --verify-tag \
  --title 'Mi aplicación 1.0.0' --notes 'Primera versión estable.'
```

La Release debe estar publicada, sin `--draft` ni `--prerelease`, con un único
`app-release.apk` completamente subido y tamaño no nulo. El manifiesto de v1.0.0
debe describir ese APK. La convención no exige SemVer, aunque el ejemplo lo usa.
No añadas `dist` ni credenciales al control de versiones.

Para actualizar: cambia el código, las versiones Android y, si procede, el
manifiesto/icono; ejecuta pruebas y compila/firma; crea un commit y una **nueva**
etiqueta (por ejemplo v1.1.0), publica su Release estable y adjunta el APK con el
nombre declarado. Refresca RobStore cuando lo permita el intervalo. No es necesario
modificar ni recompilar RobStore. No reemplaces la etiqueta anterior para actualizar.

## Seguridad y alcance aplazado

Solo se añade `INTERNET`; `usesCleartextTraffic=false`, backup deshabilitado y
reglas de extracción conservadas. Sin tokens, credenciales, servicios externos,
Firebase, servidores propios, autenticación ni repositorios privados.
No hay descarga completa de APK, PackageInstaller, acceso a aplicaciones instaladas,
comparaciones con versiones instaladas, instalación automática, canales beta/nightly,
WorkManager, notificaciones o IA. Las URLs de APK se conservan y muestran únicamente
como metadatos, sin usarlas para descargar o instalar.

La verificación real de archivo, paquete, firma e integridad y la instalación
requieren fases posteriores. Release de RobStore continúa sin firma de distribución,
como en RS-01. No se alteran otros repositorios para convertirlos en distribuibles.
