## Arquitectura

`SelfUpdateDiscovery` consulta exclusivamente el repositorio público oficial mediante las rutas REST construidas localmente. No busca topics, no exige inclusión en el catálogo y no consulta `main`. Comprueba propietario, nombre completo, URL, visibilidad, archivo, identificador del repositorio, Release publicada, fecha, canal, contrato y asset exacto. Las páginas completas tienen los límites RS-02 (10 páginas, 100 elementos/página, presupuesto de 50 solicitudes por operación; respuestas y contratos acotados). No se interpreta SemVer ni el nombre de etiqueta como versión.

`SelfUpdateRepository` conserva su caché privada en `files/self-update`, separada de `files/catalog`. Reutiliza la persistencia JSON atómica con fsync de `FileCatalogCache`; no cambia backups ni almacenamiento de usuario. Conserva la información anterior cuando una petición o escritura falla. El candidato se valida al recuperar la caché y no constituye por sí mismo autorización de descarga.

`CatalogViewModel` integra ambos repositorios y mantiene un único `DownloadCoordinator` por sesión. La identidad efectiva `Application.packageName` selecciona la variante; la versión local se obtiene mediante `PackageManager` con `AndroidInstalledApplications`, incluido `longVersionCode` desde API 28. El inicio y el retorno/resume vuelven a observar el paquete realmente instalado; no hacen peticiones REST al regresar del instalador.

`ReleaseArtifact` es el contrato común de los datos necesarios para el transporte y verificación RS-04. `CatalogApp` y `SelfUpdateCandidate` son tipos distintos. `DownloadTarget.Catalog` y `DownloadTarget.SelfUpdate` seleccionan políticas diferentes de pertenencia/origen. No se inserta ninguna aplicación artificial en el catálogo. `-1` sólo identifica en la presentación la selección propia; la autorización interna utiliza el destino explícito y el candidato validado.

## Contrato de publicación

El archivo **`robstore-update.json` debe formar parte de la etiqueta de una Release publicada** del repositorio oficial. Se obtiene por Contents API con `ref=refs/tags/<tag>` (referencia de etiqueta explícita para evitar ambigüedad con una rama del mismo nombre) y formato raw. No se admite el archivo de una rama como alternativa. La política sigue el modelo de contratos por etiqueta de RS-02; no exige adjuntar este JSON como asset.

Ejemplo documental; no es una publicación real ni un digest utilizable:

```json
{
  "schemaVersion": 1,
  "channel": "release",
  "packageName": "es.robertodorado.robstore",
  "versionCode": 2,
  "versionName": "0.2.0",
  "apkAssetName": "RobStore-release.apk",
  "sha256": "<64 caracteres hexadecimales del SHA-256 del APK firmado>"
}
```

El esquema 1 requiere todos los campos. `versionCode` es un entero JSON positivo representable en `Long`; no admite cadenas, decimales, cero ni valores desconocidos. `versionName` es texto no vacío y acotado; `apkAssetName` es el nombre exacto de un único asset APK, sin rutas. SHA-256 oficial obligatorio: 64 caracteres hexadecimales en el contrato de esa etiqueta, asociado por nombre exacto al APK. Si GitHub incluye además `digest`, debe coincidir; valores ausentes de ese campo opcional no sustituyen ni eliminan el requisito del contrato.

El APK debe estar `uploaded`, tener MIME APK u octet-stream, tamaño positivo dentro del máximo RS-04 y URL HTTPS exacta de `github.com/robdor80/RobStore/releases/download/<tag>/<asset>`, sin query, fragmentos, credenciales ni normalizaciones ambiguas. Release y metadatos inválidos se excluyen. Si hay publicaciones elegibles con información inválida y ningún candidato válido, la comprobación se considera fallida y conserva el resultado anterior. Entre publicaciones válidas del canal se escoge el mayor `versionCode`; dos publicaciones válidas con el máximo código son ambiguas y bloquean la comprobación. Los errores de red/paginación/presupuesto abortan la comprobación, conservando el resultado anterior.

Antes de descargar, después de transferir y antes de instalar se vuelve a consultar el origen, Releases, contrato y assets con cliente REST nuevo y el mismo bloqueo persistido de cuota. El candidato completo debe coincidir. Cambios en publicación, notas, código, hash, asset, tamaño o contrato que cambien el candidato bloquean el flujo. Las etiquetas siguen siendo referencias mutables de GitHub: no es una garantía criptográfica de inmutabilidad; la revalidación y el hash detectan discrepancias observadas, y Android decide la firma definitiva.

## Comparación, estados y ciclo de vida

Código remoto superior al local conocido: actualización disponible. Igual: actualizada. Inferior: no se permite actualización. Sin versión local legible o contrato remoto válido: información insuficiente/no actualización comprobable. Sin Release válida: no hay actualización comprobable, sin inventar versión a partir del tag. Errores de red mantienen versión, novedades y fecha de la última comprobación válida con advertencia explícita de información anterior.

Ajustes muestra versión instalada, canal, comprobación, fecha, límites y novedades en texto plano. Inicio presenta un aviso discreto que lleva a Ajustes. Se conservan tarjetas, tipografía, colores, botones de 48 dp y navegación RobStyle; no hay diálogos de apertura repetidos. Ajustes conserva scroll para fuente ampliada y cambios de orientación; progreso accesible y cancelación reutilizan `DownloadActions`. Sólo el texto de estado anuncia cambios mediante live region polite; las variaciones de bytes no generan anuncios repetidos.

La comprobación nunca descarga. El usuario inicia la descarga, confirma continuar y pulsa instalar; si Android exige permiso, debe concederlo y volver a pulsar. `INSTALLER_OPEN` y `UNCONFIRMED` nunca acreditan éxito, cancelación ni rechazo. El retorno consulta nuevamente la versión local. Un proceso nuevo consulta de nuevo PackageManager, limpia temporales antiguos y no recupera una capacidad de instalación del proceso anterior. Si Android termina RobStore al actualizarla, la siguiente apertura muestra su versión real. No depende de resultados de actividad para confirmar éxito.

Un APK desaparecido, alterado o caducado requiere descarga nueva. La preparación se elimina al bloquear una comprobación de seguridad. La política RS-04 de una única operación en primer plano también evita carreras entre catálogo y actualización propia. Una selección en curso o instalador abierto impide empezar otra operación. No hay servicios, WorkManager, tareas periódicas, descargas automáticas ni instalaciones silenciosas. Los datos/configuración se dejan a la actualización compatible de Android, sin modificar políticas de backup.

## Reutilización y seguridad RS-04

Se conserva un solo transporte binario, allowlist HTTPS de redirecciones/CDN, streaming acotado, comprobación de longitud, reserva de espacio, SHA-256, ruta temporal privada aleatoria, cancelación de llamada, publicación atómica, limpieza, FileProvider e instalador Android. `AndroidInstaller` no cambia. La nueva validación de artefactos acepta únicamente los dos tipos conocidos; el catálogo conserva sus propias reglas y regresiones.

Para autoactualización se exige el SHA oficial y se comparan hash calculado, tamaño, estructura APK reconocida por Android, paquete exacto, canal y `versionCode` interno igual al contrato. Antes de entregar URI se revalida publicación y se rehash/reparsea el archivo preparado (caducidad RS-04: 24 h). Se consulta la versión instalada después de verificar el archivo y otra vez en el hilo principal antes de entregar: debe conocerse y ser estrictamente menor. Cualquier igualdad, downgrade o lectura desconocida bloquea y elimina el preparado. La selección actual también se comprueba al entregar.

El parser del APK y el hash no validan criptográficamente el certificado. Android conserva la decisión final sobre firma, compatibilidad y condiciones de instalación. No se promete compatibilidad de firma, conservación absoluta de datos ni actualización física validada.

## GitHub y caché

TTL propio: 2 horas. Intervalo mínimo manual y tras fallo: 5 minutos, persistido aparte del catálogo. Repositorio y mutex de sesión impiden duplicación al recrear Activity o navegar. El reloj atrasado no provoca un bucle de peticiones. El bloqueo `blockedUntil` por Retry-After, 403/429 y cuota agotada es el mismo objeto `CatalogCache` que usa RS-02, incluso en clientes de revalidación y carga de iconos; el intervalo de intentos de catálogo no se confunde con el propio. Se conservan ETags y respuestas condicionales del cliente compartido durante la sesión. Las revalidaciones voluntarias no usan la caché de resultados de dos horas: necesitan evidencia REST actual y pueden bloquearse por cuota, sin permitir instalar offline saltándose controles.

## Pruebas y evidencias

La campaña local completa inicial ejecutó **253 Debug** y **253 Release** (214 anteriores + 39 nuevas). Detectó dos supuestos de mocks P02 incompatibles con la nueva consulta de la propia aplicación: uno en Debug (paquete local adicional) y otro sólo en Release (comprobación automática de arranque). Se adaptaron sin eliminar sus verificaciones de inventario, red ni ausencia de éxito fabricado. El contador del nuevo mock se corrigió a las cuatro observaciones reales (arranque + tres eventos).

Después se revisaron únicamente los casos afectados y las pruebas P03; la protección adicional `refs/tags/` añade una prueba más, hasta **254 casos distintos por variante, todos PASS**. La última ejecución dirigida supera **42 Debug + 42 Release**, sin fallos, errores u omitidos. No se repitieron las campañas locales completas. Los TSV en `docs/evidencias/rs05-p03/` conservan la unión de resultados con la procedencia de cada caso (`full` / `final-targeted`); los XML completos del HEAD se obtendrán de la CI automática de esta PR.

Lint local Debug y Release: **0 errores, 9 avisos preexistentes por variante** (7 `NewerVersionAvailable`, 2 `UsableSpace`). Sin avisos P03, supresiones ni cambios de dependencias. Compilación y ensamblado sin claves privadas locales mediante `-I tools/unsigned-validation.gradle`. La comprobación específica de origen supera sus pruebas en ambas variantes; lint y ensamblado incremental finales: PASS. La verificación RS-04 de ambos APK sin firma local confirma identidades, etiquetas, SDK 26/36, permisos, FileProvider limitado/no exportado, zipalign y SHA-256: PASS. Ningún APK local sin firma se presenta como instalable.

La ejecución final de GitHub Actions y su artefacto DEV se enlazan en la descripción actualizada de la [PR Draft #6](https://github.com/robdor80/RobStore/pull/6). El workflow existente no cambia: la ejecución de PR interna firma DEV con la clave temporal del runner, verifica identidades, SDK, permisos, FileProvider, zipalign y SHA-256 y sube APK, checksum, certificado público e informe. La ejecución push compila sin firma privada. La versión Release continúa sin distribución definitiva de producción.

Las nuevas pruebas usan transportes simulados, APK sintético y Robolectric: identidad, canales, contratos, drafts/prereleases, hash, versión interna, paquete/variante, selección por código, cambios de Release, cuota compartida, TTL e intervalos persistidos, offline, reinicio con versión igual/nueva, cancelación, exclusión mutua, instalación voluntaria/no confirmada, archivos alterados/desaparecidos/limpiados y recuperación. Se conserva la regresión P01/P02/RS-04.

## Pendiente P04/P05 y límites

P04: firma persistente de producción y DEV, distribución definitiva y publicación real firmada con contrato y hash del APK final; sin claves en Git. No se autoriza ni implementa en P03.

P05: prueba física de actualización compatible real y rechazo de firma incompatible, cancelación/rechazo del instalador, terminación del proceso durante actualización propia, reabrir con versión nueva y conservación de datos; TalkBack y dispositivos reales en vertical/horizontal y texto ampliado. Las simulaciones no sustituyen estas pruebas. No hay Release de producción firmada disponible que permita afirmar actualización física validada.

No se modifica otro repositorio, RobStyle, identificadores Android ni workflow de distribución DEV. La PR permanece Draft para auditoría independiente de ChatGPT.
