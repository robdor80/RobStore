# RS-05 P04 — Firma persistente y distribución mobile-first

## Alcance y cambio de requisito

Repositorio único `robdor80/RobStore`, rama `codex/rs-05-actualizaciones`, PR Draft #6,
sin fusión. Base P03 aprobada `1347de8da4fbd28a009811b93f0322b04676e28a`.
La primera entrega P04 (`8524f6d899416c37313911bce5a6f0db6e5a2643`) preparaba una ruta local.
El requisito posterior del propietario la sustituye como flujo oficial por **Android +
Codex Cloud + GitHub**, sin MSI ni Android Studio local. La guía vigente y común para todos
los proyectos es [ANDROID-MOBILE-FIRST.md](ANDROID-MOBILE-FIRST.md). La guía MSI se conserva
sólo como documento histórico opcional y no gobierna esta distribución.

No se generan claves definitivas en Codex, reciben secretos, configuran credenciales reales,
crean Releases/tags públicos ni suben APK oficiales durante esta tarea. No se avanza a P05.
Los nuevos workflows están preparados, pero no se ejecutan: requieren estar aprobados en
`main`, alta personal, entornos protegidos y activación expresa que todavía no existen.

## 1. Arquitectura y separación Release/DEV

| Uso | Paquete RobStore | Firma |
| --- | --- | --- |
| Debug habitual / CI PR interna | `es.robertodorado.robstore.debug` | Debug temporal del runner |
| DEV persistente | `es.robertodorado.robstore.debug` | Clave DEV propia, estable e independiente |
| Release oficial | `es.robertodorado.robstore` | Clave Release propia, estable |

Se conserva Gradle auditado, sin variantes adicionales, minSdk 26, target/compileSdk 36,
JDK17 para compilar y Java21 para Robolectric. Sin cambios de Kotlin, recursos o RobStyle.
VersionCode 1 / versionName 0.1.0 permanecen. Los builds normales no leen secretos de
producción; Release normal sigue sin firmar y el DEV temporal de CI continúa disponible.

La firma **oficial Actions** se hace fuera de Gradle, con `apksigner`, después del build
unsigned. El init común `unsigned-distribution.gradle` elimina las firmas y desactiva
`debuggable` en el buildType Debug destinado a distribución. El código de la aplicación
y sus plugins nunca se ejecutan con claves presentes. La configuración local histórica
sigue bloqueando su uso en CI; no se elimina ese control para dar claves a Gradle.

## 2. Workflow común, autorizaciones y permisos

Entrada manual `android-distribute.yml` → motor reutilizable
`android-distribution-engine.yml`. Otros proyectos llaman al motor central por SHA completo
aprobado; la plantilla evita copiar el motor. Configuración declarativa pequeña por app
(`.github/android-distribution.json`) y notas versionadas (`.github/release-notes.md`).

| Fase | Acceso | Condición y resultado |
| --- | --- | --- |
| guard | Lectura de repo/Actions/entornos | Propietario, dispatch manual, main actual, CI correcta, motor aprobado y entorno protegido |
| build | Sólo lectura; sin entorno ni claves | Compila APK unsigned de S en otro runner |
| sign | Entorno `android-release` o `android-dev`, revisión del propietario; token lectura | Checkout sólo herramientas centrales; firma/verifica A, publica artefacto candidato interno |
| publish | Entorno `android-publish`, otra revisión; contents:write sólo aquí | Verifica candidato aprobado, crea C/tag/Release y comprueba assets antes de hacerla visible |

La entrada por defecto es **prepare**. Publish exige selección manual, run ID de prepare,
SHA-256 exacto revisado y confirmación `PUBLICAR <tag>`. No hay publicación por push, PR,
fork, tag o `workflow_run`. Se rechazan rama no main, actor/reintento ajenos al propietario,
commit desactualizado, última CI fallida/en curso y herramientas fuera del historial
aprobado de main central. Una variable de activación ausente bloquea antes de leer claves.
El guard exige revisión del propietario y política explícita del entorno sólo para main.

Los jobs sensibles no hacen checkout de código de otras aplicaciones, no ejecutan Gradle,
no usan caché ni build scans y fijan las acciones utilizadas a SHA. El SDK se instala antes
de exponer secretos. Los PKCS12 se materializan fuera de Git, con permisos privados y se
eliminan antes del upload. Artefactos permitidos: APK firmado y metadatos públicos exactos.
Una concurrencia por repositorio serializa canales/preparación/publicación y no cancela
ejecuciones activas. Operar de una en una: la cola pendiente de GitHub puede sustituirse.

## 3. Creación, configuración y respaldo de claves desde Android

Alta personal mediante `android_owner_setup.py`, una vez por app, desde Termux del propietario.
No compila la aplicación en el teléfono. Crea dos PKCS12 RSA3072/SHA256withRSA de 10000 días
con contraseñas únicas del gestor solicitadas sin eco. No hay contraseñas de muestra/default.
Rechaza ejecución en Codex/Cloud/CI y guarda claves en el home privado de Termux fuera de Git.

El asistente genera backup GPG AES256 de ambas claves y huellas públicas; su passphrase la
pide GPG directamente y se conserva separada en el gestor. El propietario sube personalmente
**sólo el archivo cifrado** a Google Drive privado. El script exige una copia descargada,
compara su hash y ensaya descifrado/recuperación exacta antes de configurar GitHub. Codex no
recibe claves, backup descifrado, passphrases ni acceso al directorio privado del teléfono.

El mismo asistente crea entornos/reviews/política main y carga secretos mediante stdin a
GitHub CLI (cifrado de GitHub Secrets), sin pegar valores en pantallas ni mantener passwords
en argv, repositorio o logs. Los secretos se guardan a nivel de entorno, separados por
app y canal; publicar no recibe claves. Pin público de cada canal y pin del otro deben
ser diferentes y verificarse. Variables públicas: huellas, SHA del motor y activación final.
No se configura ningún secreto real durante esta entrega.

El modo `--resume` reutiliza identidades y comprueba huellas/protecciones; no regenera una
clave ya existente. Copias cifradas y recuperación del gestor deben sobrevivir a pérdida
del teléfono: Drive más una copia independiente y recuperación 2FA fuera del dispositivo.
GitHub Secrets no permite recuperar su valor. Perder la clave Release puede impedir
actualizaciones compatibles; cambiar de teléfono no justifica cambiar de certificado.
La guía común contiene los pasos secuenciales de creación, verificación, recuperación y
operación posterior, sin dependencia de MSI.

## 4. Firma y verificación

El runner aislado firma APK v2 con la clave del entorno elegido, passwords sólo por nombres
de variables seguras. Verifica con SDK35 `apksigner`, pin SHA-256, único firmante, paquete,
SDK, zipalign, no depurable y límites de tamaño/versiones. RobStore añade las comprobaciones
RS-04 completas de permisos y FileProvider no exportado/ruta limitada. DEV y Release no
comparten certificado. Faltan secretos/pins, pin incorrecto o otro paquete → bloqueo.
La clave definitiva sólo quedará comprobada después del alta y una ejecución autorizada
real en GitHub, no mediante las fixtures de esta entrega.

## 5. Versionado y orden APK/contrato/commit/tag/Release

Contador Android creciente por paquete, 1..2100000000, nombre legible `X.Y.Z` y sufijo
`-DEV` para desarrollo. Release tag `vX.Y.Z`; DEV `dev-X.Y.Z-DEV-N`. Igual/inferior al mayor
código publicado del mismo canal/paquete bloquean. No se reutiliza un código retirado ni
se incrementa ahora sin versión real aprobada. El propietario aprobará la primera estable.

Orden sin dependencia circular:

1. Código, recursos, versión, configuración y notas aprobados y con CI correcta en **S**.
2. Runner sin secretos compila unsigned desde S; otro runner firma y verifica **A**.
3. Del APK final A se extraen metadatos, hash, contrato y recibo con S/run/canal/pin/hash.
4. Artefacto interno inmutable (14 días), sin tag ni Release. El propietario revisa A y
   autoriza explícitamente su hash en un segundo dispatch; no se reconstruye.
5. Publish revalida el run, fuente actual, CI, firma, paquete, contrato, checksum, notas,
   código creciente y etiqueta nueva. Crea **C**, hijo de S, con el mismo árbol salvo
   archivos de cierre de raíz: `robstore-update.json`, `robstore-distribution.json` y,
   para estable, `robstore.json` e icono `robstore/icon.png`. Verifica la comparación por API.
6. C no se añade a main; lo hace accesible una etiqueta anotada nueva sobre C. El contrato
   está en el commit del tag como exige P03. El binario procede de S, incluidos posibles
   metadatos VCS de AGP; no se afirma que se compiló desde C. Ningún cierre modifica código
   o recursos de Android estándar. No hay recompilación después del hash.
7. Crea draft, sube exactamente A y SHA256SUMS, comprueba digest/tamaño/asset en GitHub y
   contrato desde `refs/tags/<tag>`, y sólo después publica estable o prerelease DEV.

`robstore-update.json` mantiene esquema/campos P03 sin cambios. Se genera de metadatos reales,
no de inputs de versión ni hashes provisionales. Un cambio de bytes, pin, variante,
procedencia, main o datos del candidato aborta. No se crea ningún JSON provisional en la
raíz del repositorio durante esta tarea.

GitHub no ofrece transacción única: fallos después de crear tag/draft dejan estado para
inspección expresa, sin mover tags, borrar recursos o reintentar con `--clobber`. No se
publica un draft incompleto. La guía explica recuperación y serialización. El preflight
local histórico no se mezcla con este cierre móvil de cuatro archivos.

## 6. Reutilización y descubrimiento de otras aplicaciones

Alta estándar: JSON por app, notas, CI `android.yml`, llamada al motor central fijada al
SHA auditado y el mismo asistente personal. Las identidades son propias de cada aplicación;
no se repite el diseño ni se comparte una clave universal. Actualizar el motor no cambia
claves. Módulo y SDK son configurables dentro del perfil Android estándar documentado.
Proyectos con splits/custom build requieren adaptar y auditar antes de usar secretos.

Para catálogo público: topic `robstore-app` (el asistente opcionalmente lo añade conservando
otros), propietario `robdor80`, Release estable publicada, `robstore.json` + icono en su tag
y asset APK exacto. El motor genera ese manifiesto con paquete/versiones/nombre de APK
extraídos del APK ya firmado. El hash publicado se comprueba contra digest GitHub.
RobStore **ya** descubre esas nuevas estables al refrescar, y P02/RS-04 deciden instalación
o actualización compatible. No se mantiene una lista manual de versiones/aplicaciones.
No se accede a repositorios privados ni se ofrecen prereleases DEV como estables; se
conservan caché, cuotas, revalidaciones y confirmaciones. No se altera el código del catálogo.

## 7. DEV, migración y compatibilidad

El canal Release sólo acepta su paquete; DEV usa `.debug` y certificado propio persistente.
`devDistributionConfigured=false` permanece: preparar infraestructura, credenciales o APK
de Actions no lo activa. Se necesitarán distribución DEV persistente real y autorización/
auditoría posterior de la activación. Se conserva la CI con APK Debug temporal descargable.
Instalaciones DEV temporales con otro firmante pueden requerir una desinstalación única,
con pérdida de datos locales; no se promete una migración que Android no permite.
No se modifica FileProvider, SDK, permiso de instalación ni políticas P03/RS-04.
