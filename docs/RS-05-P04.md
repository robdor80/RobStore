## Arquitectura de firma

| Uso | Paquete | Firma | Operación |
| --- | --- | --- | --- |
| Debug habitual/PR interna | `es.robertodorado.robstore.debug` | Debug temporal Android | CI/desarrollo, sin continuidad garantizada |
| DEV persistente | `es.robertodorado.robstore.debug` | Clave DEV propia del propietario | Distribución local explícita |
| Release oficial | `es.robertodorado.robstore` | Clave Release propia del propietario | Distribución local explícita |

No se crean variantes nuevas: se reutilizan los dos buildTypes auditados. El parámetro
`-ProbstoreDistribution=dev` o `release` selecciona exclusivamente la firma persistente
y desactiva `debuggable` en el APK distribuible. En modo normal no se lee configuración
privada, Debug conserva su firma temporal y Release queda **sin firmar**. Las pruebas
Debug/Release y las identidades/recursos propios de cada buildType siguen iguales.
No se cambia minSdk 26, target/compileSdk 36, Java 17/21, versionCode 1 ni versionName 0.1.0.
DEV conserva el sufijo `-DEV`.

El modo persistente admite exactamente una tarea solicitada:
`:app:assembleDebug` para DEV o `:app:assembleRelease` para Release. No admite abreviaturas,
combinación con tests, lint, otro ensamblado o tareas diferentes. Está bloqueado con
`CI=true` o `GITHUB_ACTIONS=true`. Sin el parámetro no se activa, aunque exista el archivo
privado. No se concede acceso a claves reales a PR/forks ni se añade workflow de publicación.
La opción debe venir de `-P` en la invocación: una propiedad persistida en gradle.properties
o heredada del entorno no basta para activar distribución.
El modo persistente también rechaza configuration cache, build scans y logging DEBUG
antes de leer secretos; la herramienta desactiva además la caché de compilación.

`ROBSTORE_SIGNING_FILE` debe señalar un archivo privado existente **fuera del repositorio**.
Los keystores también deben existir fuera del repositorio. Se requieren las dos huellas
públicas distintas; se abre sólo el keystore del canal elegido, se comprueban contraseña,
alias, acceso a clave privada y SHA-256 del certificado antes de configurar AGP.
Se rechazan claves/certificados equivocados y overrides que anulen la configuración.
Se utiliza PKCS12 con firma APK v2 (Android >=26); la herramienta final exige v2 válido,
un único firmante, huella esperada, zipalign, identidad, SDK y APK no depurable.

La validación reduce errores operativos; una persona que modifique Gradle o ejecute
herramientas ajenas puede producir otros binarios. Sólo el APK que supere el procedimiento
completo se considera candidato oficial. Un `assembleRelease` normal no lo es.

## Configuración privada del MSI y custodia

El propietario genera personalmente **dos claves independientes** después de la auditoría,
con `keytool` del JDK 17, RSA 3072, SHA256withRSA y validez de 10000 días. Debe comprobar
que la fecha final cubre la vida prevista de RobStore. Android Studio también puede crear
keystores; la ruta reproducible aquí usa `keytool` y PKCS12.

Ubicación sugerida: directorio privado del perfil del propietario, fuera de RobStore,
sin sincronización automática ni acceso de otros usuarios; proteger con ACL de Windows
y cifrado de disco BitLocker. No usar carpetas compartidas, Escritorio sincronizado,
Drive/OneDrive ni directorios accesibles desde entornos cloud. No enviar archivos,
contraseñas, capturas de configuración o claves a ChatGPT/Codex.

El archivo Java Properties privado (UTF-8 sin BOM) contiene los siguientes **nombres** por cada prefijo
`release.` y `dev.` (sin valores predeterminados ni contraseñas de ejemplo):

| Campo | Contenido local |
| --- | --- |
| `storeFile` | Ruta absoluta del PKCS12, usando `/` en Windows |
| `storePassword` | Contraseña real elegida personalmente |
| `keyAlias` | Alias de esa identidad |
| `keyPassword` | Contraseña real de la clave; PKCS12 de keytool normalmente comparte la del almacén |
| `certificateSha256` | SHA-256 público, 64 hexadecimales sin `:` |

Java Properties interpreta escapes: utilizar editor local que respete este formato;
si la contraseña contiene `\`, escaparlo como `\\`. No introducir contraseñas en
argumentos `-P`, terminal, variables persistentes de CI ni historial. El archivo privado
es una opción explícitamente permitida; contiene secretos en reposo y requiere los mismos
controles y copias cifradas que el keystore. No subirlo como artefacto ni al soporte.
El nombre de variable de entorno contiene sólo una ruta. No ejecutar Gradle con `--debug`,
build scans, plugins no auditados o scripts de inicio externos que puedan inspeccionar secretos.
No compartir logs privados sin revisarlos localmente.

Elegir contraseñas largas, únicas y aleatorias con un gestor de contraseñas; sin valores
por defecto. Mantener al menos dos copias cifradas verificadas de cada clave, archivo de
configuración, alias y huellas, en soportes separados físicamente. Guardar las credenciales
de recuperación separadas de los soportes; ensayar recuperación en un equipo local confiable.
Tras pérdida del MSI: recuperar copia cifrada, restaurar permisos, comprobar huellas y firmar
una copia local de prueba antes de publicar. No regenerar una clave pensando que conserva
la identidad. **Perder la clave Release puede impedir futuras actualizaciones compatibles**
de instalaciones existentes. No se implementa rotación de firmas ni recuperación de claves.
Una clave comprometida requiere un análisis aparte; no sustituirla silenciosamente.

## Herramientas de distribución

`tools/distribution.py` nunca crea tags, Releases ni sube archivos. Subcomandos:

- `build`: exige árbol limpio (incluidos untracked no ignorados), ejecuta Gradle sin caché
  de compilación/configuración y con `--rerun-tasks`, comprueba HEAD/limpieza de nuevo,
  verifica firma real y copia el APK a un directorio nuevo fuera de Git. No sobrescribe
  candidatos. Genera contrato real, `SHA256SUMS` y recibo de procedencia en ese directorio.
- `prepare`: verifica otra vez APK, certificado y contrato del candidato, exige estar en
  el commit exacto de compilación y una versión superior al contrato oficial anterior
  proporcionado, o declaración explícita de primera publicación. Copia sólo contrato y
  recibo a la raíz del repositorio. No calcula hashes ficticios ni vuelve a compilar.
- `verify`: compara **todos** los campos del contrato con metadatos y hash reales del APK
  firmado. Rechaza cualquier diferencia, cambio de bytes, firma o paquete incorrectos.
- `preflight`: exige árbol limpio, commit final distinto del de compilación y descendiente,
  disponible para revisión en el repositorio oficial, y mismo árbol Git completo salvo
  `robstore-update.json` y `robstore-distribution.json`. Verifica de nuevo el APK/contrato,
  huella y recibo. Exige etiqueta nueva, coherente con versión, tanto local como remota.
  Consulta mediante `gh api` **todas** las Releases publicadas del canal (paginación), lee
  los contratos de `refs/tags/<tag>`, comprueba identidad y asset, y exige superar todos
  sus versionCode. Red, permisos, contrato anterior ausente/incoherente o lectura fallida
  bloquean el proceso. Sin publicaciones exige `--first-publication` explícito.

`--certificate` siempre es una huella **pública verificada por el propietario**, obtenida
de su clave local; no una huella copiada de un APK desconocido. La comprobación online final
impide que `--first-publication` o un contrato anterior obsoleto eludan códigos ya publicados.
El checker no interpreta el nombre del tag para sustituir versionCode. En `preflight` se
exige `v<versionName>` para Release (tres componentes numéricos) y
`dev-<versionName>-<versionCode>` para DEV.

## Orden sin dependencia circular

1. Auditar/aprobar el código y la versión. Ejecutar pruebas sin claves. Incorporar todo
   cambio de código, recursos, Gradle, documentación y notas de versión a un commit **S**,
   con árbol limpio. Publicar/revisar S en la rama autorizada; no etiquetar todavía.
2. En el MSI, sobre S, compilar/firmar una sola vez con `build`. Guardar APK final, contrato,
   SHA256SUMS y recibo fuera del checkout. Registrar S, huella pública y herramientas.
3. `prepare` compara el APK final y crea en Git contrato + recibo; revisar y crear commit
   **C** exclusivamente con esos dos archivos. El recibo registra S, canal, certificado
   público y hash del APK. El APK **procede de S**, no de una compilación de C.
4. No recompilar ni firmar de nuevo. `robstore-update.json` y el recibo son archivos de
   raíz no consumidos por el build Android; no hay estampado del SHA Git en recursos.
   La igualdad de todo el resto del árbol entre S y C garantiza que no se modificaron
   entradas versionadas de código/recursos. No modificar scripts/dependencias locales,
   SDK/JDK, archivos ignorados de build ni configuración privada entre pasos. Entorno
   local confiable y SDK/herramientas auditados siguen siendo requisitos.
   AGP puede incluir información de control de versiones en metadatos del APK: debe
   corresponder a S. No se afirma que el APK se compiló desde C ni que reconstruir C
   produzca bytes idénticos.
5. Subir C para revisión sin tag ni Release. Ejecutar `preflight` con el mismo APK firmado.
   Si cambia **cualquier** otro archivo entre S y C, abandonar el candidato, preparar un
   nuevo S y repetir con directorio nuevo. No corregirlo sobrescribiendo hashes/recibos.
6. Tras autorización expresa del propietario, crear una etiqueta anotada/verificable
   sobre **C**, idealmente firmada con identidad Git del propietario. No moverla después.
   P03 leerá el contrato desde esa etiqueta. Publicar exactamente el APK ya verificado,
   SHA256SUMS y notas revisadas. No ejecutar un nuevo build desde C para sustituir el APK.

No existe dependencia del APK respecto al contrato: ambos archivos de cierre se añaden
después y no se empaquetan. El recibo no cambia el esquema P03, es evidencia adicional.
No se añade ningún contrato real/provisional a la raíz durante P04.
Una reconstrucción puede producir bytes distintos: la continuidad es la del APK conservado,
no una promesa de compilación reproducible bit a bit.

## Versionado y publicación

Contador creciente **por paquete**; DEV y Release son líneas independientes. Mantener
versionCode entre 1 y 2100000000 (límite práctico Android), versionName legible de Release
`X.Y.Z`, DEV `X.Y.Z-DEV`. P03 sólo ofrece códigos estrictamente superiores; igual no es
actualización, inferior se rechaza. Un cambio de versionName no permite reutilizar código.
No incrementar ahora sin publicación real aprobada. Para la primera estable el propietario
aprobará nombre/código tras inventariar instalaciones previas; no se presupone que 1 sea
suficiente para cualquier instalación existente. Las futuras versiones aumentan el contador
incluso si se retira una publicación. Android puede permitir reinstalación de mismo código,
pero el proceso oficial y P03 no la ofrecen como actualización.

Repositorio oficial `robdor80/RobStore`; Release pública estable: no draft ni prerelease.
DEV persistente: prerelease explícita con contrato `dev` y paquete `.debug`. Cada publicación
incluye etiqueta sobre C, APK firmado exacto, código/nombre, contrato en C, checksum y notas.
Revisar desde GitHub la etiqueta/commit y los bytes descargados antes de anunciarla; no borrar
ni sustituir assets de versiones ya distribuidas. Reglas de protección de etiquetas y firmas
Git verificables son recomendables y las habilitará el propietario por separado.

Los comandos de escritura de GitHub y creación/push de tags se reservan a una guía posterior
con autorización expresa. Esta entrega termina con la validación previa y no ejecuta
publicación. El procedimiento requiere serializar publicaciones: `preflight` es evidencia
puntual, no un bloqueo transaccional de GitHub. Repetirlo inmediatamente antes de la acción
manual autorizada; si alguien publica otra versión entre medias, detenerse y reevaluar.

## Compatibilidad P03, DEV y migración

No se modifica el contrato esquema 1 ni el código de autoactualización. Se conservan canal,
paquete, código creciente, hash oficial, revalidación de origen, RS-04, FileProvider y la
decisión final de Android sobre firma/compatibilidad. La herramienta de publicación añade
comprobación criptográfica local; no convierte el parser Android P03 en un verificador
criptográfico de certificados. Release sólo actualiza Release y DEV sólo DEV.

`devDistributionConfigured` sigue **false**. Ni tener credenciales locales, ni pasar un
build, ni subir un artefacto temporal a Actions lo activa. Para activarlo será necesaria
una autorización posterior, distribución DEV persistente realmente publicada/verificada,
huellas públicas documentadas, fuente/prerelease correcta, pruebas físicas y auditoría del
cambio de código correspondiente. P04 no adelanta esas operaciones ni fija una huella falsa.

DEV anteriores con firmas temporales distintas pueden requerir **una desinstalación única**
y reinstalación manual del futuro APK persistente. Android no admite una actualización
normal con un firmante incompatible. Desinstalar puede borrar datos locales; no prometer
conservación ni migración que Android no permita. Release y DEV pueden coexistir, conservando
sus datos separados; nunca compartir claves para resolver una migración.

## CI, seguridad y validación

La CI conserva tests Debug/Release, lint, ensamblado, comprobaciones SDK/identidades/permisos,
FileProvider, zipalign, hashes, regresiones y artefacto Debug instalable con firma temporal
para PR internas autorizadas. Push/forks continúan sin firma privada. Sólo se añaden fixtures
Python y análisis del historial; checkout obtiene el historial completo para ese análisis.
No hay secretos reales ni workflow automático de distribución.

`check_distribution_secrets.py` revisa nombres de archivos privados y bloques PEM privados
en todos los blobs alcanzables del historial local; CI obtiene todas las ramas/tags del
checkout completo. `.gitignore` cubre keystores, PKCS12/JCEKS y configuración privada.
El análisis no certifica ausencia de cualquier secreto arbitrario u objetos inaccesibles;
se revisan además diff y logs para contraseñas literales. Los errores de la herramienta no
imprimen salida de firmadores ni configuración; las fixtures usan contraseñas aleatorias
en entorno de subproceso, archivos temporales privados y limpieza automática.

Resultados locales: **254 Debug + 254 Release**, todos PASS, sin fallos/errores/omitidos.
Lint: **0 errores y 9 avisos preexistentes por variante** (7 NewerVersionAvailable,
2 UsableSpace), sin supresiones. Ensamblado normal Debug/Release y verificador RS-04: PASS.
**17 tests unitarios Python + 6 fixtures con APK real firmado**: PASS. **12 invocaciones
Gradle dirigidas**: 10 bloqueos esperados y 2 builds persistentes con claves efímeras;
ambos APK aceptan su huella y rechazan la otra. No aparece la contraseña aleatoria en
stdout/stderr de las herramientas; tampoco en los logs daemon comprobados de la fase final.
Se conserva cada caso auditado: RS-03 99, RS-04 158, P01 196 y P03 254 por variante.
`actionlint` y `git diff --check`: PASS. Lectura real de Releases: cero publicaciones
del canal Release y cero del canal DEV en el momento de la comprobación.

La campaña Android se reintentó tras corregir sólo el proxy externo del runtime Robolectric;
tras su éxito se hicieron comprobaciones dirigidas de firmado/ensamblado. La fixture de
override se ajustó para anular la firma tarde: el init script habitual RS-04 la elimina
antes de que el modo P04 explícito la configure de nuevo, y no simula una anulación tardía.
La fase final pasa con una fixture que realmente intenta quitarla después de configurar P04.
El getter público de configuration cache usado por el guard genera un aviso de deprecación
al compilar el script con Gradle 8.13; no es un error ni un aviso de lint Android. Revisarlo
al actualizar Gradle, conservando la prohibición de serializar credenciales.

[Evidencias locales](evidencias/rs05-p04/README.md). La ejecución CI del HEAD final y el
artefacto Debug temporal se enlazan con su estado definitivo en la descripción de la
[PR Draft #6](https://github.com/robdor80/RobStore/pull/6), sin otro commit que repita la
campaña sólo para actualizar enlaces. La CI ejecuta toda la campaña sobre el commit enviado.

## Límites P05

No se valida aquí la clave definitiva ni una actualización física real; ninguna fixture
es certificado de producción. El propietario aún debe generar/custodiar claves en MSI,
aprobar versión/publicación y ejecutar operaciones locales. P05 requiere autorización:
actualización física con firma persistente, rechazo real de firma incorrecta, cancelación,
terminación/reinicio de proceso, conservación de datos y accesibilidad/dispositivos reales.
No se han modificado RobStyle ni otros repositorios; no se ha publicado distribución,
creado etiqueta pública, recibido secretos del propietario ni activado DEV.
